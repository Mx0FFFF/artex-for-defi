# Cross-chain messages, bridges, and asynchronous DeFi state

Use this reference only when the scoped protocol sends value or instructions between chains, or accepts calls from a gateway, relayer, messenger, or token pool. First identify the **actual** bridge version, source and destination chain IDs, gateway addresses, remote counterpart, trust model, message identifier, finality rule, and retry semantics. A repository containing an interface is not proof that the deployed integration uses it.

The cases below are **hypotheses to test**, not findings. The listed tests are derived audit probes. A finding requires a reproducible violation under the protocol's real configuration and a control case that succeeds or fails as expected.

## Message authenticity and authority

| Failure mode | Preconditions and test | Control / evidence | Primary source |
| --- | --- | --- | --- |
| **Unproven message accepted after initialization or upgrade.** A sentinel root, timestamp, or mapping default is mistaken for an authenticated proof. | Trace `initialize`/upgrade storage into the exact proof predicate. On a local deployment or pinned fork, submit an unproven message with a changed recipient, amount, and origin; assert it cannot move funds or execute an arbitrary call. Repeat after each upgrade path. | Show the committed root, proof status, storage before/after, and the accepted/rejected call trace. A test with a mocked verifier that simply returns true proves only the mock. Nomad's own analysis describes how an accepted zero root let unproven messages pass `Replica.process`. | [Nomad root cause analysis](https://medium.com/nomad-xyz-blog/nomad-bridge-hack-root-cause-analysis-875ad2e5aacd) |
| **Wrong source chain, remote sender, or gateway accepted.** `msg.sender` is a gateway, not the original caller; an address alone does not identify the same entity across chains. | For each privileged receive path, vary source chain, source contract, gateway, and payload independently. Assert only the configured tuple can mint, release, upgrade, or change accounting. Check both local and remote roles where the same address is used. | A genuine gateway/receiver integration must be used or faithfully mocked with its authenticated metadata. Check deployed peer configuration, not just source defaults. OpenZeppelin warns that same-address contracts on different chains can be different authorities; Chainlink assigns source-chain and sender validation to receiver applications. | [OpenZeppelin cross-chain access control](https://docs.openzeppelin.com/contracts/4.x/crosschain), [Chainlink CCIPReceiver security notes](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/ccip-receiver) |
| **Signatures or proof attestations omit critical fields.** A valid authorization can be reused with a different destination, amount, token, recipient, nonce, bridge instance, or validator set. | Build a valid locally signed message and mutate one field at a time. Test duplicate signatures, stale validator-set epochs, threshold changes, and signatures from the wrong domain. Assert the signed digest binds all execution-relevant fields and every signer is counted once. | Distinguish a code flaw from an accepted governance/trust assumption. Report compromised keys or concentrated signers as a threat model dependency unless a code/configuration path makes the threshold bypassable. Ronin's commissioned bridge assessment explicitly checks chain IDs, amount, receiver, nonce, replay invalidation, and spoofing. | [Ronin bridge security assessment](https://cdn.axieinfinity.com/ronin-doc/REP-final-20220621T172752Z.pdf), [Ronin bridge redesign](https://blog.roninchain.com/p/the-ronin-bridge-is-open-) |

## Replay, finality, and execution state

| Failure mode | Preconditions and test | Control / evidence | Primary source |
| --- | --- | --- | --- |
| **A delivered message executes twice, or a retry creates a second credit.** | Model `unseen → verified → in-progress → success` plus the protocol's failure/retry states. Deliver the same authenticated message twice; retry once after a receiver failure; assert one net mint/release/claim. If the app uses a message ID, verify it is scoped to the correct origin and destination. | Protocol layers differ: some prevent replay at delivery, while some require application idempotency. Do not report missing app-level tracking where the actual gateway guarantees exactly-once execution and the integration cannot bypass it. CCIP says successful messages cannot replay but application idempotency may still be required; Wormhole Executor requires app-owned replay protection. | [CCIP receiver notes](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/ccip-receiver), [Wormhole Executor replay protection](https://wormhole.com/docs/protocol/infrastructure/relayers/executor-vs-sr/) |
| **Out-of-order delivery violates application state.** | Create two individually valid messages whose effects depend on order, such as collateral credit then borrow, position open then close, or governance configuration then action. Deliver the second first, retry the first, and compare final assets and liabilities with the intended sequence. | Verify what the deployed bridge actually guarantees. CCIP 2.0 manual execution says it does not enforce sender ordering; Wormhole's receiver guide explicitly calls for deciding how out-of-order VAAs are handled. An app that queues or rejects later messages safely has no ordering bug. | [CCIP manual execution FAQ](https://docs.chain.link/ccip/concepts/manual-execution), [Wormhole receiver guide](https://wormhole.com/docs/products/messaging/guides/core-contracts/) |
| **Sequence/nonce replay protection assumes finality it does not have.** | Check whether uniqueness is based on `(emitter chain, emitter address, sequence)`, VAA hash, message ID, or app nonce. Simulate a source reorg or two payloads sharing a sequence under the documented consistency level; assert an old or conflicting message cannot double-credit or block the correct one. | Wormhole states sequence uniqueness depends on finality and recommends VAA-hash tracking for non-finalized messages. A single-fork test cannot prove reorg behavior; use explicit alternate message histories and document the finality assumption. | [Wormhole VAA format and finality](https://wormhole.com/docs/protocol/infrastructure/vaas/), [Wormhole replay protection](https://wormhole.com/docs/protocol/infrastructure/relayers/executor-vs-sr/) |
| **Premature or stale-proof withdrawal finalization.** | For optimistic bridges, test each gating condition independently: message existed on source, proof matches the current accepted output, challenge/proof maturity time passed, dispute resolved, and withdrawal not already finalized. Try finalization just before each threshold and after invalidating a proof. | Use the exact bridge version and its actual challenge parameters. A deliberately mocked `true` proof is not evidence of an onchain bypass. OP Stack's current withdrawal path describes initiate, prove, and finalize as separate states and checks replay prevention on finalization. | [OP Stack withdrawal flow](https://docs.optimism.io/op-stack/bridging/withdrawal-flow) |
| **Failed execution is silently consumed or mishandled on retry.** | Force the destination callback to revert, run out of callback gas, or return an unexpected value. Confirm whether the message remains retryable, whether tokens and instruction execution are atomic, and whether the retry can credit value twice. Repeat with a successful callback. | Inspect recorded execution state, not just the outer transaction receipt: CCIP can record `FAILURE` inside a successful outer transaction. In OpenZeppelin's bridge base, silent failure from `_processMessage` can mark a message received and prevent retry. | [CCIP manual execution states](https://docs.chain.link/ccip/concepts/manual-execution), [OpenZeppelin BridgeFungible notes](https://docs.openzeppelin.com/contracts/5.x/api/crosschain) |

## Value conservation and composition

| Failure mode | Preconditions and test | Control / evidence | Primary source |
| --- | --- | --- | --- |
| **Unbacked wrapped supply or duplicate release.** | Identify whether the lane is lock/release, lock/mint, or burn/mint. Track source escrow/burn, destination mint/release, pending messages, fees, decimals, and supply across both sides. Assert that successful transfers have exactly one corresponding debit and credit in the protocol's units. Mutate token behavior (fee-on-transfer, rebasing, false return) only if supported by the scoped bridge. | Do not impose a simple `escrow == supply` equality on a model with multiple lanes, in-flight messages, fees, or authorized minting. Check the actual pool and token implementation. Chainlink documents distinct custody models and `lockOrBurn`/`releaseOrMint` gates. | [Chainlink token-pool models](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/token-pool-overview), [Chainlink TokenPool API](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/token-pool) |
| **Inbound callback reenters accounting or credits before value exists.** | For programmable token transfer, trace token availability, callback, and app state updates. Use a malicious receiver/token on a local harness to reenter the same or adjacent receive/claim path. Assert message state and balances stay consistent and a failed callback does not leave a spendable credit. | Verify bridge-level atomicity before claiming an app bug: CCIP states token plus receiver execution is atomic for its failure path. Its receiver documentation still calls out application-level external-call/reentrancy risks. | [CCIP manual execution](https://docs.chain.link/ccip/evm/tutorials/application-developers/manual-execution), [CCIP receiver notes](https://docs.chain.link/ccip/evm/api-reference/v2.0.0/ccip-receiver) |
| **Rate-limit or unit conversion bypass across lanes.** | Exercise per-chain, per-direction limits with token decimals and values near the bucket capacity; test config changes, fast-finality lanes, and parallel transfers. Assert that the intended limit cannot be bypassed by splitting, rounding, or switching a lane where the same risk budget is meant to apply. | Some limits are intentionally lane-local and config changes may refill buckets immediately; these are documented behaviors, not bugs by themselves. Show the actual policy and a net transfer beyond it. | [Chainlink CCIP rate limits](https://docs.chain.link/ccip/evm/concepts/cross-chain-token/rate-limits/overview) |

## Reproduction method for asynchronous protocols

1. Draw a state machine for **both chains**: lock/burn, emitted message, verification/finality, destination execution, failure/retry, release/mint, and cancellation/refund if supported. Write the safety property separately from the liveness property. A stuck message can be a liveness failure without unbacked minting; an unauthorized mint is a safety failure.
2. On local deployments or two pinned Foundry forks, exercise a valid baseline first, then one adversarial transition at a time. `vm.createSelectFork(url, blockNumber)` and `vm.selectFork` can select fixed chain states, but switching forks does **not** create real offchain attestations or relay messages. Model the relayer/gateway faithfully, and verify its actual proof checks separately. [Foundry fork cheatcodes](https://www.getfoundry.sh/reference/cheatcodes/create-select-fork)
3. Use a handler with actors and ghost counters for deposits, burns, mints, releases, failures, and retries. Compare the counters against onchain balances and consumed message IDs after every transition. Track how often handlers actually reach each state; a fuzz run that only reverts or never executes the receive path has no meaningful bridge coverage. [Foundry invariant-testing guide](https://www.getfoundry.sh/guides/invariant-testing)
4. Preserve source and destination chain IDs, block numbers, gateway/peer addresses, message bytes and IDs, proof/attestation provenance, role configuration, before/after balances, execution state, and the exact test command. If the test substitutes a mock proof, mark the authentication assumption as unverified and do not claim a production exploit.
